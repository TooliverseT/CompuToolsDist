Cron의 역사와 Linux Cron vs Quartz의 구조적 차이는 [The Complete Guide to Cron Expressions: Everything a Developer Must Know About Scheduling](https://www.compu-tools.com/blog/2026-02-25-cron/)에서 다뤘다. 이 글은 그 다음 단계다. 문법을 알아도 막히는 것들 — 특수문자를 어떻게 조합하는지, 어떤 표현식이 어떤 상황에 적합한지, 그리고 왜 내가 쓴 표현식이 의도대로 동작하지 않는지 — 에 집중한다. 시스템 운영, 데이터 파이프라인, 백엔드 서비스, CI/CD까지 도메인별 실전 예제를 통해 Cron Expression을 실용적으로 익히는 것이 목표다.

## 특수문자 조합: 단순한 것 같지만 함정이 있다

기본 특수문자 네 가지(`*`, `,`, `-`, `/`)는 누구나 안다. 문제는 조합이다. 같은 결과처럼 보이지만 동작이 다른 표현식들이 존재한다.

### `/` 스텝: 시작점이 결과를 바꾼다

`/`는 "A부터 B 간격으로"를 의미한다. `*/5`는 `0/5`와 같다 — 0을 기점으로 5 간격이므로 0, 5, 10, 15, ...분에 실행된다. 그런데 `3/5`로 쓰면 3, 8, 13, 18, ...분이 된다. 시작점이 달라지는 것이다.

```bash
*/5  * * * *   # 0, 5, 10, 15, 20 ... 분 (매시 12회)
3/5  * * * *   # 3, 8, 13, 18, 23 ... 분 (매시 12회, 하지만 시작이 다름)
1/15 * * * *   # 1, 16, 31, 46 분 (매시 4회)
0/30 * * * *   # 0, 30 분 (매시 2회)
```

실무에서 `*/15`를 쓸 때는 대부분 정각 기준(0, 15, 30, 45분)을 원하는 경우다. 만약 부하 분산을 위해 정각을 피하고 싶다면 `7/15`(7, 22, 37, 52분)처럼 시작점을 의도적으로 옮기는 것이 좋다.

### `-`와 `/`의 조합: 범위 내 스텝

`-`와 `/`를 함께 쓰면 "범위 내에서 간격 실행"이 된다.

```bash
0 9-17/2 * * 1-5   # 월~금, 9시부터 17시까지 2시간 간격 정각 (9, 11, 13, 15, 17시)
0/10 8-18 * * *    # 매일 8~18시 사이, 10분 간격 (8:00, 8:10, 8:20 ... 18:50)
```

여기서 주의할 점이 하나 있다. `9-17/2`는 9를 기점으로 2 간격이라 9, 11, 13, 15, 17이 된다. 하지만 `8-18/3`은 8, 11, 14, 17이 되고 18은 포함되지 않는다(8+3n이 18을 넘기 때문). 의도한 시각이 정확히 포함되는지는 직접 나열해보거나 [Cron Expression Parser](https://www.compu-tools.com/cron/)로 확인해야 한다.

### `,`와 `-`의 혼합: 불연속 범위

```bash
0 8,12,18 * * *         # 8시, 12시, 18시 정각
0 8-10,14-16 * * *      # 8, 9, 10, 14, 15, 16시 정각
0 0 1,15 * *            # 매월 1일과 15일 자정
0 0 * * 1,3,5           # 월, 수, 금 자정
```

`8-10,14-16`처럼 범위와 리스트를 혼합하는 패턴은 업무 시간대 스케줄링에 자주 쓰인다. 오전 블록과 오후 블록을 각각 범위로 묶고 `,`로 연결하면 된다.

## Quartz 전용 특수문자: L, W, #

Quartz는 Linux Cron에 없는 특수문자를 추가로 지원한다. [Quartz 공식 문서](http://www.quartz-scheduler.org/documentation/quartz-2.3.0/tutorials/crontrigger.html)에 상세 명세가 있지만, 핵심만 정리하면 다음과 같다.

**`L` (Last)** — day-of-month와 day-of-week 필드에서 사용 가능하다.

```
# day-of-month에서 L: 해당 월의 마지막 날
0 0 0 L * ?        # 매월 마지막 날 자정

# day-of-month에서 L-n: 마지막 날에서 n일 전
0 0 0 L-3 * ?      # 매월 마지막 날로부터 3일 전 자정 (예: 31일 달이면 28일)

# day-of-week에서 nL: 해당 달의 마지막 n번째 요일
0 0 0 ? * 6L       # 매월 마지막 금요일 자정 (Quartz: 6=금)
```

**`W` (Weekday)** — day-of-month에서만 유효하며, 지정한 날짜에 가장 가까운 평일을 의미한다.

```
0 0 9 15W * ?      # 매월 15일에 가장 가까운 평일 오전 9시
                   # 15일이 토요일이면 14일(금), 일요일이면 16일(월) 실행
```

**`#` (Nth weekday)** — day-of-week에서만 유효하며, "해당 달의 n번째 특정 요일"을 지정한다.

```
0 0 10 ? * 2#1     # 매월 첫 번째 월요일 오전 10시 (Quartz: 2=월)
0 0 20 ? * 6#3     # 매월 세 번째 금요일 오후 8시
```

`#` 표현식은 "격주 실행"처럼 보이는 요구사항에 사용하기 쉬운데, 실제로는 "n번째 주"가 아니라 "n번째 해당 요일"이다. 5번째 금요일(`6#5`)이 없는 달에는 실행이 누락되므로 주의해야 한다.

## 표현식을 오독하기 쉬운 패턴들

문법은 맞지만 직관과 다르게 동작하는 표현식들이 있다. 실수가 반복되는 패턴을 정리했다.

### day-of-month + day-of-week 동시 지정: Linux vs Quartz의 차이

Linux Cron에서 두 필드를 모두 지정하면 **OR 조건**으로 동작한다.

```bash
# Linux: "매월 1일 OR 매주 월요일" 자정 실행
0 0 1 * 1
```

이 표현식은 1일이 월요일이 아니어도 1일에 실행되고, 월요일이 1일이 아니어도 월요일에 실행된다. "매월 1일이면서 월요일일 때만"(AND)을 원한다면 Linux Cron으로는 표현 불가능하다 — 스크립트 내부에서 날짜를 검사해야 한다.

Quartz는 이 충돌을 `?`로 해소한다. 둘 중 하나를 `?`로 설정하면 나머지 하나만 조건으로 작동한다.

```
# Quartz: 매월 1일만 (월요일과 무관)
0 0 0 1 * ?

# Quartz: 매주 월요일만 (날짜와 무관)
0 0 0 ? * MON
```

### "매시 30분" 표현의 두 가지 함정

`30 * * * *`는 정확하다. 그런데 `0/30 * * * *`와 `*/30 * * * *`는 어떤 차이가 있을까? 결과는 동일하게 0분과 30분이다. 하지만 의도를 명확히 전달하는 쪽은 `0/30`이다 — "0분부터 30분 간격"이라는 뜻이 분명하기 때문이다. `*/30`도 관습적으로 통용되지만, 일부 파서에서 `*`를 "현재 시각 기준"으로 해석하는 경우가 있어 `0/30`을 권장하는 팀도 있다.

### 요일 번호: 플랫폼마다 다르다

| 요일 | Linux Cron | Quartz | AWS EventBridge |
|------|-----------|--------|-----------------|
| 일요일 | 0 (또는 7) | 1 | 1 (또는 SUN) |
| 월요일 | 1 | 2 | 2 (또는 MON) |
| 토요일 | 6 | 7 | 7 (또는 SAT) |

Linux에서 `1-5`는 월~금이지만, Quartz에서 `1-5`는 일~목이다. 플랫폼을 바꿀 때 요일 표현식을 그대로 복사하면 조용하게 잘못된 요일에 실행된다. Quartz를 쓸 때는 숫자 대신 `MON-FRI` 같은 이름 표기를 쓰는 것이 실수를 줄이는 데 도움이 된다.

## 도메인별 실전 예제 모음

### 1. 시스템 운영 & 인프라

```bash
# --- 백업 ---
0 2 * * *          # 매일 새벽 2시 전체 DB 백업 (가장 일반적인 패턴)
0 2 * * 0          # 주간 풀 백업 (일요일 새벽 2시), 평일은 증분 백업과 병행
0 3 1 * *          # 매월 1일 새벽 3시 월간 아카이브

# --- 로그 관리 ---
0 0 * * *          # 매일 자정 로그 로테이션
30 23 * * *        # 매일 23:30 전날 로그 압축 후 S3 업로드
0 4 * * 0          # 일요일 새벽 4시 오래된 로그 삭제 (30일 이상)

# --- 시스템 모니터링 ---
*/5 * * * *        # 5분마다 헬스체크 엔드포인트 ping
*/1 * * * *        # 1분마다 프로세스 생존 여부 확인 (watchdog)
0 * * * *          # 매시 정각 디스크 사용량 수집
7 * * * *          # 매시 7분 메모리/CPU 리포트 (정각 집중 회피)

# --- 캐시 관리 ---
0 3 * * *          # 매일 새벽 3시 전체 캐시 웜업
*/30 * * * *       # 30분마다 TTL 만료 캐시 정리
```

### 2. 데이터 파이프라인 & ETL

```bash
# --- 정기 수집 ---
0 1 * * *          # 매일 새벽 1시 외부 API 데이터 수집 (일 배치)
0 */4 * * *        # 4시간마다 증분 데이터 동기화
*/15 9-18 * * 1-5  # 평일 업무 시간(9~18시) 중 15분마다 실시간 피드 수집

# --- 집계 & 리포트 ---
0 6 * * 1-5        # 평일 오전 6시 전날 지표 집계 (업무 시작 전 완료 목표)
0 8 * * 1          # 월요일 오전 8시 주간 리포트 생성
0 7 1 * *          # 매월 1일 오전 7시 전월 월간 리포트 생성
0 7 1 1 *          # 매년 1월 1일 오전 7시 연간 리포트

# --- 데이터 정합성 ---
30 2 * * *         # 매일 새벽 2:30 데이터 무결성 검사
0 1 * * 0          # 일요일 새벽 1시 데이터 웨어하우스 통계 갱신 (ANALYZE)
0 0 * * * [ "$(date -d tomorrow +\%d)" = "01" ] && /scripts/month_end_close.sh
                   # 매월 마지막 날 자정 마감 처리 (Linux Cron에서 마지막 날 처리)
```

### 3. 백엔드 서비스

```bash
# --- 알림 & 이메일 ---
0 9 * * 1          # 월요일 오전 9시 주간 뉴스레터 발송
0 9,18 * * 1-5     # 평일 9시, 18시 업무 알림 발송
0 8 * * *          # 매일 오전 8시 오늘의 할일 리마인더
30 17 * * 5        # 금요일 17:30 주말 전 마감 알림

# --- 세션 & 토큰 관리 ---
0 * * * *          # 매시간 만료된 세션 정리
*/10 * * * *       # 10분마다 만료 임박 토큰 리프레시 큐 처리
0 2 * * *          # 매일 새벽 2시 블랙리스트 토큰 DB 정리

# --- 결제 & 정산 ---
0 0 1 * *          # 매월 1일 자정 구독 갱신 처리
30 23 * * *        # 매일 23:30 당일 거래 마감 정산
0 9 * * 1-5        # 평일 오전 9시 전날 결제 실패 건 재시도
0 0 * * 1          # 매주 월요일 자정 주간 인보이스 생성
```

### 4. CI/CD & DevOps

```bash
# --- 빌드 & 배포 ---
0 2 * * 1-5        # 평일 새벽 2시 야간 빌드 (nightly build)
0 6 * * 1-5        # 평일 오전 6시 스테이징 자동 배포
0 22 * * 5         # 금요일 22시 주간 릴리스 배포 (트래픽 최저 시점)

# --- 테스트 자동화 ---
0 1 * * *          # 매일 새벽 1시 전체 회귀 테스트 (nightly regression)
0 */6 * * *        # 6시간마다 스모크 테스트
*/30 9-18 * * 1-5  # 평일 업무 시간 중 30분마다 API 통합 테스트

# --- 인프라 관리 ---
0 3 * * 0          # 일요일 새벽 3시 의존성 업데이트 PR 자동 생성
0 4 1 * *          # 매월 1일 새벽 4시 보안 취약점 스캔
0 5 * * *          # 매일 새벽 5시 Docker 이미지 정리 (dangling images)
30 2 * * 0         # 일요일 새벽 2:30 SSL 인증서 만료 확인
```

## Quartz 실전 예제: Spring @Scheduled

Spring에서 `@Scheduled`를 사용할 때 가장 많이 쓰이는 패턴들을 Linux Cron 등가 표현과 함께 정리했다. Quartz는 초(second) 필드가 첫 번째 자리임을 기억하자.

```java
// 매일 자정
@Scheduled(cron = "0 0 0 * * ?")       // Linux 등가: 0 0 * * *

// 평일 오전 9시
@Scheduled(cron = "0 0 9 ? * MON-FRI") // Linux 등가: 0 9 * * 1-5

// 매월 1일 새벽 2시
@Scheduled(cron = "0 0 2 1 * ?")       // Linux 등가: 0 2 1 * *

// 매월 마지막 날 23시 (L 문자 활용)
@Scheduled(cron = "0 0 23 L * ?")

// 매월 첫 번째 월요일 오전 10시 (# 문자 활용)
@Scheduled(cron = "0 0 10 ? * MON#1")

// 30초마다 (Linux Cron으로는 불가능한 패턴)
@Scheduled(cron = "0/30 * * * * ?")

// 타임존 지정 (서울 기준 오전 9시)
@Scheduled(cron = "0 0 9 ? * MON-FRI", zone = "Asia/Seoul")
```

`zone` 속성은 Spring 4.0부터 지원되며, 서버가 UTC로 운용되더라도 특정 타임존 기준으로 스케줄을 정의할 수 있어 실무에서 매우 유용하다. 자세한 내용은 [Spring 공식 스케줄링 문서](https://docs.spring.io/spring-framework/reference/integration/scheduling.html)를 참고하자.

## 표현식 검증: 배포 전 체크리스트

표현식을 작성했다면 배포 전에 다음을 확인하자. [Cron Expression Parser](https://compu-tools.com/cron/)를 활용하면 이 체크리스트의 대부분을 시각적으로 빠르게 검증할 수 있다.

**1단계 — 파서로 실행 시각 확인:** 표현식을 파서에 입력하고 다음 10~20회 실행 시각을 직접 눈으로 확인한다. 의도한 시각과 다른 경우가 생각보다 자주 나온다.

**2단계 — 타임존 명시:** 파서에서 실제 운용 환경의 타임존을 선택해 실행 시각을 재확인한다. 특히 서버가 UTC이고 의도한 시각이 로컬 타임존 기준이라면 반드시 이 단계를 거쳐야 한다.

**3단계 — 경계값 확인:** 월말(28/29/30/31일), DST 전환일(미국 기준 3월 둘째 주 일요일·11월 첫째 주 일요일) 전후로 실행 시각이 어떻게 달라지는지 확인한다.

**4단계 — 실행 간격 vs 실행 시간 비교:** 작업 실행에 걸리는 시간이 스케줄 간격보다 길 가능성이 있다면 `flock`(Linux) 또는 `concurrencyPolicy: Forbid`(Kubernetes)를 적용한다.

**5단계 — 부하 분산 검토:** 팀 내 모든 cron 작업의 실행 시각이 특정 시각(특히 자정, 매시 정각)에 집중되어 있지 않은지 확인한다. 의도적으로 분산시키는 것만으로 인프라 비용을 줄일 수 있다.

```bash
# 나쁜 예: 모든 작업이 자정에 집중
0 0 * * * /scripts/backup.sh
0 0 * * * /scripts/report.sh
0 0 * * * /scripts/cleanup.sh

# 좋은 예: 의도적으로 분산
0  0 * * * /scripts/backup.sh
7  0 * * * /scripts/report.sh
23 0 * * * /scripts/cleanup.sh
```

## Linux Cron으로 표현할 수 없는 것들

다음 요구사항은 Linux Cron 표현식만으로는 구현이 불가능하다. 우회책과 함께 정리했다.

| 요구사항 | Linux Cron | 우회책 |
|---------|-----------|--------|
| 매월 마지막 날 | ❌ | `date -d tomorrow +%d = 01` 스크립트 조건 |
| n번째 특정 요일 | ❌ | `date +%W` 스크립트 조건, 또는 Quartz `#` |
| 가장 가까운 평일 | ❌ | Quartz `W` 문자 사용 |
| 30초마다 | ❌ | Quartz 초 필드, 또는 systemd timer |
| 특정 날짜 단 한 번 | ❌ | `at` 명령어, 또는 직접 삭제하는 스크립트 |
| AND 조건 (날짜 AND 요일) | ❌ | 스크립트 내부 조건 분기 |

이 한계에 자주 부딪힌다면 Quartz(Java/Spring 환경)나 systemd timer(Linux 시스템 서비스)를 검토할 시점이다. systemd timer는 `OnCalendar` 지시어를 통해 Linux Cron보다 훨씬 풍부한 표현이 가능하고, 의존성 관리와 로깅도 통합되어 있다.

## 마치며

Cron Expression은 외울 것이 많아 보이지만, 결국 패턴의 반복이다. 특수문자 조합 규칙 몇 가지를 제대로 이해하면 대부분의 스케줄을 표현할 수 있고, 표현할 수 없는 경우에는 어떤 우회책이 있는지 알면 충분하다.

표현식을 작성할 때마다 [Cron Expression Parser](https://compu-tools.com/cron/)로 실행 시각을 먼저 확인하는 습관을 들이자. 머릿속으로 "맞겠지"라고 넘기는 그 순간이 새벽 장애 알림의 시작이 되는 경우가 생각보다 많다.
